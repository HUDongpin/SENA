# SENA.HK Research Pilot Delivery Candidate

SENA — Social-Epistemic Nexus Analytics — is a local research-pilot delivery candidate for combining social-network analysis, epistemic-network analysis, and traceable social-epistemic bridge evidence.

Current status: local research pilot delivery candidate with a runnable enterprise readiness loop, not a completed production SaaS cutover. The intended handoff is still a stable researcher walkthrough and reproducibility-review package, while the local enterprise runtime makes auth, RBAC teams, server-side project persistence, import adapters, reliability workflows, group-comparison validation suites, notification outbox plus webhook delivery, signed collaboration pub/sub bridge delivery, signed managed-database sync bridge delivery, signed audit/SIEM, backup/object-storage, alerting, email, IdP/provisioning bridge evidence, native adapter certification, SaaS operations readiness records, release-gate review records, and go-live rehearsal records runnable before institution cutover. A clean handoff requires the full local verification gate to pass after any local `next dev` or `next start` server has been stopped.

The core demo route is `/workspace/sena`. It builds:

- `S`: person-person social interaction matrix
- `W`: code-code epistemic co-occurrence matrix
- `B` / `B_PC`: person-to-code contribution matrix (`B` is the compatibility alias)
- `B_CP`: code-to-person bridge matrix, independently estimated from valid target-person evidence or set to the transpose-compatible `B_PC` fallback
- `G`: person-code-pair contribution matrix
- `A_fusion`: weighted typed matrix `[alpha*S gamma*B_PC; gamma*B_CP beta*W]`; independent `B_CP` evidence activates directed bridge semantics
- jSNA social-network manifest and metrics through local `sna.js`, including actor centrality, graph connectivity, communities, components, and S matrix
- jENA manifest and standalone ENA report outputs through local `jena-js`, including projected unit points, code node positions, connection counts, line weights, and W-matrix handoff evidence
- jENA/jSNA/SENA runtime bundle export with data-contract audit, SENA method protocol, visual grammar artifact, development plan, pilot package manifest, production page contract, runtime consistency checks, standalone jENA ENA report, jENA concept-pair handoff checks against the SENA `W` matrix, artifact-level evidence coverage for jENA/jSNA/SENA handoff files, fusion math audit, demo walkthrough, demo verification checklist and compatibility audit, pilot-readiness checks, standalone coding-reliability gate, claim-readiness gate, temporal runtime trace with per-window matrix fingerprints, and single-file review packet with its own completeness audit for reproducibility review
- temporal windows with per-window jENA/jSNA runtime trace, S/W/B/B_PC/B_CP/G/A_fusion matrix fingerprints, visible A_fusion checksums, adjacent-window S/W/B/B_PC/B_CP/G/A_fusion transition evidence, Temporal Fusion Arc S/W/B/G story view, evidence snippets, evidence ledger export, and JSON/Markdown reports with data-contract, completeness, and formula audits

### Enterprise SSO Configuration

The `/login` and `/register` SSO buttons use `/api/auth/sso`. The pages query `/api/auth/sso?status=1`; configured providers start a real OAuth/OIDC authorization-code flow with PKCE through the GET redirect endpoint and return through `/api/auth/sso/callback`, while providers without secrets keep the local pilot fallback so walkthroughs remain runnable. In `NODE_ENV=production`, that local fallback is disabled by `sena-enterprise-sso-fallback-policy/v1` unless `SENA_ALLOW_LOCAL_SSO_FALLBACK=1` is set for an explicitly approved pilot-only deployment. Registration links such as `/register?inviteCode=...` prefill the invitation code, and SSO state carries that code through callback so an invited Google, ORCID, or institution SSO user joins the invited team when the provider email matches the invitation. Deployment operators can call `/api/auth/sso?status=1&preflight=1` to run `sena-enterprise-sso-preflight/v1`, which verifies provider configuration, resolves discovery or explicit endpoints, checks callback URL/scopes, stores redacted preflight audit evidence, and feeds the production readiness `oidc-provider` gate.

Configure one or more providers with:

```bash
SENA_APP_URL=https://your-sena-host.example
SENA_SSO_GOOGLE_CLIENT_ID=...
SENA_SSO_GOOGLE_CLIENT_SECRET=...
# optional, defaults to Google's OIDC discovery URL
SENA_SSO_GOOGLE_DISCOVERY_URL=...

SENA_SSO_ORCID_CLIENT_ID=...
SENA_SSO_ORCID_CLIENT_SECRET=...
# optional, defaults to ORCID's OIDC discovery URL
SENA_SSO_ORCID_DISCOVERY_URL=...

SENA_SSO_INSTITUTION_CLIENT_ID=...
SENA_SSO_INSTITUTION_TENANT_ID=...
SENA_SSO_INSTITUTION_CLIENT_SECRET=...
SENA_SSO_INSTITUTION_CLIENT_SECRET_REF=institution-vault/sena/sso-client-secret
SENA_SSO_INSTITUTION_CLIENT_SECRET_VERSION=sso-client-secret-rotation-YYYY-MM
SENA_IDENTITY_SECRET_ROTATION_CADENCE_DAYS=180
SENA_SSO_INSTITUTION_DISCOVERY_URL=https://idp.example.edu/.well-known/openid-configuration
```

For providers without discovery metadata, set `SENA_SSO_<PROVIDER>_ISSUER`, `SENA_SSO_<PROVIDER>_AUTHORIZATION_URL`, `SENA_SSO_<PROVIDER>_TOKEN_URL`, `SENA_SSO_<PROVIDER>_USERINFO_URL`, and `SENA_SSO_<PROVIDER>_JWKS_URL`. SENA validates signed OIDC `id_token` values against JWKS plus issuer, audience, nonce, expiry, and issued-at claims before accepting the SSO callback. Check `/api/auth/sso?status=1` or `/api/sena/governance/health` to see which providers are configured, which environment variables are still missing, and whether the local SSO fallback policy is enabled. Run `/api/auth/sso?status=1&preflight=1&provider=google` or the matching provider before handoff; governance records `auth.sso.preflight.pass/fail` without storing client secrets. In production, set non-secret `SENA_SSO_INSTITUTION_TENANT_ID` so tenant approval evidence is bound to the institution IdP tenant or app registration, set `SENA_IDENTITY_SECRET_ROTATION_CADENCE_DAYS` to the institution-approved SSO/provisioning rotation cadence from 1 to 180 days, and pair each configured identity secret with a non-secret secret-store reference such as `SENA_SSO_INSTITUTION_CLIENT_SECRET_REF` plus a non-secret rotation version such as `SENA_SSO_INSTITUTION_CLIENT_SECRET_VERSION`; readiness stores only hashes and never stores or exports the secret value.

Password login has local enterprise brute-force protection. Defaults are 5 failed attempts in a 15-minute window followed by a 15-minute lockout; override with `SENA_AUTH_LOCKOUT_MAX_FAILURES`, `SENA_AUTH_LOCKOUT_WINDOW_MINUTES`, and `SENA_AUTH_LOCKOUT_MINUTES`. Registration and password-reset confirmation enforce `sena-enterprise-password-policy/v1`: at least 12 characters, letters and numbers, no common weak-password fragments, and no email local-part reuse. Audit entries use `auth.login.failed` and `auth.login.locked` with email hashes and domains rather than raw email addresses.

Auth endpoints also use file-backed local API rate limiting. Defaults are `SENA_AUTH_API_RATE_LIMIT_MAX_REQUESTS=20` per `SENA_AUTH_API_RATE_LIMIT_WINDOW_SECONDS=60`, password reset defaults to `SENA_PASSWORD_RESET_RATE_LIMIT_MAX_REQUESTS=5` per `SENA_PASSWORD_RESET_RATE_LIMIT_WINDOW_SECONDS=900`, and SSO defaults to `SENA_SSO_RATE_LIMIT_MAX_REQUESTS=30` per `SENA_SSO_RATE_LIMIT_WINDOW_SECONDS=300`. Rate-limit keys are SHA-256 hashed before storage, over-limit events audit as `security.rate_limit`, and `apiRateLimits` are excluded from team backups as transient security state.

Cookie-auth mutating endpoints require `/api/auth/csrf`; send the returned token in `x-sena-csrf-token` for session-authenticated `POST`, `PUT`, `PATCH`, and `DELETE` requests. Bearer-token provisioning, SCIM, and ops service calls do not use CSRF. Failures audit as `security.csrf.fail`, and tokens are bound to the current session using `SENA_CSRF_SECRET` or `SENA_SESSION_SECRET`.

Authenticator MFA is available through the `/workspace/sena` Enterprise runtime Account security panel and `/api/auth/mfa`. Authenticated users can start setup, enter the current TOTP code to enable MFA, check status, and disable MFA from the workbench; API clients can `POST {"action":"setup"}` to receive a one-time TOTP setup secret and `otpauth://` URL, `POST {"action":"enable","setupToken":"...","code":"123456"}` to enable MFA, `GET` to check status, and `DELETE {"code":"123456"}` to disable it. MFA login returns `202` from `/api/auth/login` with a challenge token until a valid TOTP code is submitted. MFA secrets are sealed with AES-256-GCM; set `SENA_MFA_ENCRYPTION_KEY` or `SENA_SESSION_SECRET` in production-like environments so governance health does not rely on the local fallback key.

Session lifecycle management is also exposed in the `/workspace/sena` Enterprise runtime Account security panel. Signed-in users can list active sessions, identify the current session, revoke individual non-current sessions, or revoke all other sessions from the workbench; API clients can use `GET /api/auth/sessions` and `DELETE /api/auth/sessions` with a CSRF token for the same lifecycle controls.

Password reset is available through `/api/auth/password-reset` and `/reset-password`. `POST {"action":"request","email":"..."}` queues a reset without revealing whether the account exists. `POST {"action":"confirm","resetToken":"...","password":"..."}` applies `sena-enterprise-password-policy/v1`, updates the password, revokes existing sessions, clears failed-login lockouts, and records audit evidence. For local smoke tests only, set `SENA_PASSWORD_RESET_EXPOSE_TOKEN=1` to return a local reset token and URL in the API response; production-like deployments should keep that unset and connect an institution-approved email or notification provider.

Notifications are available through `/api/sena/notifications`. The local enterprise runtime queues an in-app outbox record for team invitations, password-reset requests, project comments, reliability reviews, and validation reviews without storing raw recipient email addresses. Authenticated users can query their visible notifications and mark them as read; team managers can query team-scoped delivery evidence and `POST` the same route to run the webhook delivery/retry worker. When `SENA_ENTERPRISE_STATE_STORE=postgres` is active, the notifications route reads and updates the primary Postgres state row for list, read status, notification delivery status, sealed email-delivery queue status, and audit evidence instead of mutating `.sena-enterprise/enterprise-db.json`. Set `SENA_NOTIFICATION_WEBHOOK_URL`, optional `SENA_NOTIFICATION_WEBHOOK_SECRET`, `SENA_NOTIFICATION_WEBHOOK_MAX_ATTEMPTS`, and `SENA_NOTIFICATION_WEBHOOK_TIMEOUT_MS` to send redacted signed notification payloads to an institution-approved event bus, email bridge, or workflow service. Production-like deployments should still document the final email provider, retention policy, and monitoring owner.

Collaboration pub/sub delivery is available through `/api/sena/projects/:projectId/collaboration`. The local SSE stream remains available for single-runtime browser updates, while presence, comment, comment-resolution, and adjudication actions also enqueue signed external delivery events when `SENA_COLLABORATION_PUBSUB_WEBHOOK_URL` is configured. When `SENA_ENTERPRISE_STATE_STORE=postgres` is active, collaboration route mutations use the Postgres primary-state row first and then mirror comments, active presence, adjudications, and refreshed reliability coverage to indexed Postgres tables for collaboration reads and ops evidence. Team managers can call `POST {"action":"deliver-pubsub","force":true}` on the collaboration route to send `sena-enterprise-collaboration-pubsub-webhook/v1` payloads with `x-sena-webhook-event: collaboration.publish`, endpoint-hash evidence, retry status, and optional HMAC signing from `SENA_COLLABORATION_PUBSUB_WEBHOOK_SECRET`. Use `SENA_COLLABORATION_PUBSUB_WEBHOOK_MAX_ATTEMPTS` and `SENA_COLLABORATION_PUBSUB_WEBHOOK_TIMEOUT_MS` to tune replay behavior; team backups exclude `collaborationEvents` as transient delivery queue state.

Organization provisioning is available through `/api/sena/provisioning`. Set `SENA_PROVISIONING_TOKEN` and call the endpoint with `Authorization: Bearer ...` to upsert teams, users, SSO identities, and memberships from an institution IdP. In production, also set non-secret `SENA_PROVISIONING_TOKEN_SECRET_REF` secret-store custody evidence, `SENA_PROVISIONING_TOKEN_VERSION` rotation evidence, and `SENA_IDENTITY_LIFECYCLE_OWNER_MODE` to `scim`, `idp`, or `hybrid` so the platform decision record explicitly binds lifecycle ownership before SCIM/IdP ownership evidence can pass. Provisioned records store source, external ID, and last-sync metadata; audit logs store counts and hashes rather than raw credentials. The runtime enforces the same last-active-team-manager guardrail used by manual membership changes.

SCIM 2.0 provisioning is available through `/api/sena/scim/v2/ServiceProviderConfig`, `/api/sena/scim/v2/Users`, and `/api/sena/scim/v2/Groups` using the same bearer token. The bridge accepts standard SCIM User/Group payloads, the standard Enterprise User organization extension, and the SENA extension schemas `urn:sena:params:scim:schemas:extension:enterprise:2.0:User` and `urn:sena:params:scim:schemas:extension:enterprise:2.0:Group` for role-aware team memberships, SSO subject mapping, and group member roles. SCIM `active:false` maps to suspended memberships while preserving the last-active-team-manager guardrail.

Ops monitoring is available through `/api/sena/ops/status`, `/api/sena/ops/metrics`, `/api/sena/ops/readiness`, `/api/sena/ops/cdn`, `/api/sena/ops/postgres`, `/api/sena/ops/object-storage`, `/api/sena/ops/jobs/worker-contract`, `/api/sena/ops/observability`, `/api/sena/ops/observability/probe`, `/api/sena/ops/production-evidence`, `/api/sena/ops/deployment`, `/api/sena/ops/native-adapters`, `/api/sena/ops/saas-operations`, `/api/sena/ops/go-live-rehearsal`, `/api/sena/ops/platform-decisions`, `/api/sena/ops/release-gate`, and `/api/sena/ops/alerts`. Set `SENA_OPS_TOKEN` for bearer-token access from deployment monitors; without it, the monitor endpoints require an authenticated SENA session. Platform decision and release-gate reviews always require a session plus team-management RBAC. The metrics endpoint emits Prometheus-style gauges such as readiness, storage writability, backup age, collaboration pub/sub/database-sync/object-storage/backup/alert webhook configuration, Postgres/object-storage/job-queue/observability live probe readiness, production evidence manifest completeness, collection counts, queue counts, ops-token configuration, request p95, request error rate, route sample counts, worker-contract readiness, and observability exporter readiness. The production evidence endpoint emits `sena-enterprise-production-evidence-manifest/v1`, aggregating redacted artifact custody for the Vercel production preflight, Postgres, object storage, CDN, server job queue, external worker contract, observability, the production performance budget, and the conference load rehearsal. Upload object-storage delivery is available through `/api/sena/uploads`. ## Interpretation Guardrails

- `A_fusion` is a normalized typed adjacency model, not a causal model.
- `B` aliases `B_PC`; `B_CP` uses independently declared target-person evidence when available and otherwise uses the audited `B_PC`-transpose fallback. Independent `B_CP` makes `A_fusion` directed and requires directed analysis or declared symmetrization.
- Explanatory and ENA-space layouts use position for readability.
- Joint mode uses declared `A_fusion` embedding operators: Laplacian eigenmaps, MDS + Schoenberg, or commute-time; distance claims must carry operator, delta, dimension, deterministic seed, metric exactness, and stress.
- Human review and coding-reliability documentation are required before using exported interpretations for publication, assessment, or instructional decisions.
