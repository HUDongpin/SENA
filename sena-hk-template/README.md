### Enterprise SSO Configuration

The `/login` and `/register` SSO buttons use `/api/auth/sso`. The pages query `/api/auth/sso?status=1`; configured providers start a real OAuth/OIDC authorization-code flow with PKCE through the GET redirect endpoint and return through `/api/auth/sso/callback`, while providers without secrets keep the local pilot fallback so walkthroughs remain runnable. In `NODE_ENV=production`, that local fallback is disabled by `sena-enterprise-sso-fallback-policy/v1` unless `SENA_ALLOW_LOCAL_SSO_FALLBACK=1` is set for an explicitly approved pilot-only deployment. Registration links such as `/register?inviteCode=...` prefill the invitation code, and SSO state carries that code through callback so an invited Google, ORCID, or institution SSO user joins the invited team when the provider email matches the invitation. Deployment operators can call `/api/auth/sso?status=1&preflight=1` to run `sena-enterprise-sso-preflight/v1`, which verifies provider configuration, resolves discovery or explicit endpoints, checks callback URL/scopes, stores redacted preflight audit evidence, and feeds the production readiness `oidc-provider` gate.

Configure one or more providers with:

```bash
SENA_APP_URL=https://your-sena-host.example
SENA_SSO_GOOGLE_CLIENT_ID=...
SENA_SSO_GOOGLE_CLIENT_SECRET=...
# optional, defaults to Google's OIDC discovery URL
SENA_SSO_GOOGLE_DISCOVERY_URL=...

SENA_SSO_ORCID_CLIENT_ID=...
SENA_SSO_ORCID_CLIENT_SECRET=...
# optional, defaults to ORCID's OIDC discovery URL
SENA_SSO_ORCID_DISCOVERY_URL=...

SENA_SSO_INSTITUTION_CLIENT_ID=...
SENA_SSO_INSTITUTION_TENANT_ID=...
SENA_SSO_INSTITUTION_CLIENT_SECRET=...
SENA_SSO_INSTITUTION_CLIENT_SECRET_REF=institution-vault/sena/sso-client-secret
SENA_SSO_INSTITUTION_CLIENT_SECRET_VERSION=sso-client-secret-rotation-YYYY-MM
SENA_IDENTITY_SECRET_ROTATION_CADENCE_DAYS=180
SENA_SSO_INSTITUTION_DISCOVERY_URL=https://idp.example.edu/.well-known/openid-configuration
```

For providers without discovery metadata, set `SENA_SSO_<PROVIDER>_ISSUER`, `SENA_SSO_<PROVIDER>_AUTHORIZATION_URL`, `SENA_SSO_<PROVIDER>_TOKEN_URL`, `SENA_SSO_<PROVIDER>_USERINFO_URL`, and `SENA_SSO_<PROVIDER>_JWKS_URL`. SENA validates signed OIDC `id_token` values against JWKS plus issuer, audience, nonce, expiry, and issued-at claims before accepting the SSO callback. Check `/api/auth/sso?status=1` or `/api/sena/governance/health` to see which providers are configured, which environment variables are still missing, and whether the local SSO fallback policy is enabled. Run `/api/auth/sso?status=1&preflight=1&provider=google` or the matching provider before handoff; governance records `auth.sso.preflight.pass/fail` without storing client secrets. In production, set non-secret `SENA_SSO_INSTITUTION_TENANT_ID` so tenant approval evidence is bound to the institution IdP tenant or app registration, set `SENA_IDENTITY_SECRET_ROTATION_CADENCE_DAYS` to the institution-approved SSO/provisioning rotation cadence from 1 to 180 days, and pair each configured identity secret with a non-secret secret-store reference such as `SENA_SSO_INSTITUTION_CLIENT_SECRET_REF` plus a non-secret rotation version such as `SENA_SSO_INSTITUTION_CLIENT_SECRET_VERSION`; readiness stores only hashes and never stores or exports the secret value.

Password login has local enterprise brute-force protection. Defaults are 5 failed attempts in a 15-minute window followed by a 15-minute lockout; override with `SENA_AUTH_LOCKOUT_MAX_FAILURES`, `SENA_AUTH_LOCKOUT_WINDOW_MINUTES`, and `SENA_AUTH_LOCKOUT_MINUTES`. Registration and password-reset confirmation enforce `sena-enterprise-password-policy/v1`: at least 12 characters, letters and numbers, no common weak-password fragments, and no email local-part reuse. Audit entries use `auth.login.failed` and `auth.login.locked` with email hashes and domains rather than raw email addresses.

Auth endpoints also use file-backed local API rate limiting. Defaults are `SENA_AUTH_API_RATE_LIMIT_MAX_REQUESTS=20` per `SENA_AUTH_API_RATE_LIMIT_WINDOW_SECONDS=60`, password reset defaults to `SENA_PASSWORD_RESET_RATE_LIMIT_MAX_REQUESTS=5` per `SENA_PASSWORD_RESET_RATE_LIMIT_WINDOW_SECONDS=900`, and SSO defaults to `SENA_SSO_RATE_LIMIT_MAX_REQUESTS=30` per `SENA_SSO_RATE_LIMIT_WINDOW_SECONDS=300`. Rate-limit keys are SHA-256 hashed before storage, over-limit events audit as `security.rate_limit`, and `apiRateLimits` are excluded from team backups as transient security state.

Cookie-auth mutating endpoints require `/api/auth/csrf`; send the returned token in `x-sena-csrf-token` for session-authenticated `POST`, `PUT`, `PATCH`, and `DELETE` requests. Bearer-token provisioning, SCIM, and ops service calls do not use CSRF. Failures audit as `security.csrf.fail`, and tokens are bound to the current session using `SENA_CSRF_SECRET` or `SENA_SESSION_SECRET`.

Authenticator MFA is available through the `/workspace/sena` Enterprise runtime Account security panel and `/api/auth/mfa`. Authenticated users can start setup, enter the current TOTP code to enable MFA, check status, and disable MFA from the workbench; API clients can `POST {"action":"setup"}` to receive a one-time TOTP setup secret and `otpauth://` URL, `POST {"action":"enable","setupToken":"...","code":"123456"}` to enable MFA, `GET` to check status, and `DELETE {"code":"123456"}` to disable it. MFA login returns `202` from `/api/auth/login` with a challenge token until a valid TOTP code is submitted. MFA secrets are sealed with AES-256-GCM; set `SENA_MFA_ENCRYPTION_KEY` or `SENA_SESSION_SECRET` in production-like environments so governance health does not rely on the local fallback key.

Session lifecycle management is also exposed in the `/workspace/sena` Enterprise runtime Account security panel. Signed-in users can list active sessions, identify the current session, revoke individual non-current sessions, or revoke all other sessions from the workbench; API clients can use `GET /api/auth/sessions` and `DELETE /api/auth/sessions` with a CSRF token for the same lifecycle controls.

Password reset is available through `/api/auth/password-reset` and `/reset-password`. `POST {"action":"request","email":"..."}` queues a reset without revealing whether the account exists. `POST {"action":"confirm","resetToken":"...","password":"..."}` applies `sena-enterprise-password-policy/v1`, updates the password, revokes existing sessions, clears failed-login lockouts, and records audit evidence. For local smoke tests only, set `SENA_PASSWORD_RESET_EXPOSE_TOKEN=1` to return a local reset token and URL in the API response; production-like deployments should keep that unset and connect an institution-approved email or notification provider.

Notifications are available through `/api/sena/notifications`. The local enterprise runtime queues an in-app outbox record for team invitations, password-reset requests, project comments, reliability reviews, and validation reviews without storing raw recipient email addresses. Authenticated users can query their visible notifications and mark them as read; team managers can query team-scoped delivery evidence and `POST` the same route to run the webhook delivery/retry worker. Set `SENA_NOTIFICATION_WEBHOOK_URL`, optional `SENA_NOTIFICATION_WEBHOOK_SECRET`, `SENA_NOTIFICATION_WEBHOOK_MAX_ATTEMPTS`, and `SENA_NOTIFICATION_WEBHOOK_TIMEOUT_MS` to send redacted signed notification payloads to an institution-approved event bus, email bridge, or workflow service. Production-like deployments should still document the final email provider, retention policy, and monitoring owner.

Collaboration pub/sub delivery is available through `/api/sena/projects/:projectId/collaboration`. The local SSE stream remains available for single-runtime browser updates, while presence, comment, comment-resolution, and adjudication actions also enqueue signed external delivery events when `SENA_COLLABORATION_PUBSUB_WEBHOOK_URL` is configured. Team managers can call `POST {"action":"deliver-pubsub","force":true}` on the collaboration route to send `sena-enterprise-collaboration-pubsub-webhook/v1` payloads with `x-sena-webhook-event: collaboration.publish`, endpoint-hash evidence, retry status, and optional HMAC signing from `SENA_COLLABORATION_PUBSUB_WEBHOOK_SECRET`. Use `SENA_COLLABORATION_PUBSUB_WEBHOOK_MAX_ATTEMPTS` and `SENA_COLLABORATION_PUBSUB_WEBHOOK_TIMEOUT_MS` to tune replay behavior; team backups exclude `collaborationEvents` as transient delivery queue state.

Organization provisioning is available through `/api/sena/provisioning`. Set `SENA_PROVISIONING_TOKEN` and call the endpoint with `Authorization: Bearer ...` to upsert teams, users, SSO identities, and memberships from an institution IdP. In production, also set non-secret `SENA_PROVISIONING_TOKEN_SECRET_REF` secret-store custody evidence, `SENA_PROVISIONING_TOKEN_VERSION` rotation evidence, and `SENA_IDENTITY_LIFECYCLE_OWNER_MODE` to `scim`, `idp`, or `hybrid` so the platform decision record explicitly binds lifecycle ownership before SCIM/IdP ownership evidence can pass. Provisioned records store source, external ID, and last-sync metadata; audit logs store counts and hashes rather than raw credentials. The runtime enforces the same last-active-team-manager guardrail used by manual membership changes.

SCIM 2.0 provisioning is available through `/api/sena/scim/v2/ServiceProviderConfig`, `/api/sena/scim/v2/Users`, and `/api/sena/scim/v2/Groups` using the same bearer token. The bridge accepts standard SCIM User/Group payloads, the standard Enterprise User organization extension, and the SENA extension schemas `urn:sena:params:scim:schemas:extension:enterprise:2.0:User` and `urn:sena:params:scim:schemas:extension:enterprise:2.0:Group` for role-aware team memberships, SSO subject mapping, and group member roles. SCIM `active:false` maps to suspended memberships while preserving the last-active-team-manager guardrail.

Ops monitoring is available through `/api/sena/ops/status`, `/api/sena/ops/metrics`, `/api/sena/ops/readiness`, `/api/sena/ops/deployment`, `/api/sena/ops/native-adapters`, `/api/sena/ops/saas-operations`, `/api/sena/ops/go-live-rehearsal`, `/api/sena/ops/platform-decisions`, `/api/sena/ops/release-gate`, and `/api/sena/ops/alerts`. Set `SENA_OPS_TOKEN` for bearer-token access from deployment monitors; without it, the monitor endpoints require an authenticated SENA session. Platform decision and release-gate reviews always require a session plus team-management RBAC. The JSON status reports runtime uptime, storage readability/writability, write-lock health, write-before backup existence, upload blob integrity, collaboration pub/sub webhook configuration and queue health, database-sync webhook configuration, object-storage webhook configuration, backup freshness, backup webhook configuration, alert webhook configuration, queue counters, and collection counts. The metrics endpoint emits Prometheus-style gauges such as readiness, storage writability, backup age, collaboration pub/sub/database-sync/object-storage/backup/alert webhook configuration, collection counts, queue counts, and ops-token configuration. The readiness endpoint returns a production-gate artifact with blocking checks for storage, lock health, write-before backup, ops token, backup freshness, signed backup webhook delivery, signed alert webhook delivery, signed database-sync delivery, signed upload object-storage delivery, signed collaboration pub/sub delivery, OIDC, provisioning, notification webhook signing, institution email webhook signing, audit, and RBAC, plus advisory platform-decision checks for production `NODE_ENV`, managed database/object storage adapter choice, upload missing/corrupt/orphan evidence, secret hardening, validation evidence, deployment package evidence, and monitoring ownership. The deployment endpoint emits `sena-enterprise-organization-deployment/v1`, a redacted handoff package with required env inventory, service endpoints, readiness/governance summaries, OIDC provider status, platform-decision ownership, `sena-enterprise-platform-decision-register/v1`, latest release-gate review and verification evidence, and verification commands; the native-adapters, SaaS-operations, and go-live-rehearsal endpoints emit standalone `sena-enterprise-native-adapter-certification/v1`, `sena-enterprise-saas-operations-readiness/v1`, and `sena-enterprise-go-live-rehearsal/v1` dossiers for platform-owner review before cutover. The register tracks full SaaS backend operations until the institution platform owner approves the bridge model or replaces it with native managed database, object storage, pub/sub, email, alerting, audit, backup, and IdP adapters. `POST /api/sena/ops/platform-decisions` records `sena-enterprise-platform-decision-acceptance/v1` evidence for accepted, rejected, native-adapter-required, or superseded decisions; accepted bridge records are counted in the deployment package, native adapter certification, governance evidence, and SaaS operations readiness. Set `SENA_PLATFORM_SAAS_OPERATING_MODEL_APPROVED=1` only after that platform-owner approval is recorded. Secret values are excluded, endpoint values are hashed, and secret hashing is disabled to avoid creating reusable secret fingerprints. The alerts endpoint emits `sena-enterprise-ops-alerts/v1` with firing critical/warning items derived from ops status and readiness, plus alerting ownership evidence from `SENA_ALERTING_OWNER`, optional `SENA_ALERTING_CHANNEL`, and optional `SENA_ALERTING_RUNBOOK_URL`; `POST {"action":"deliver"}` sends a signed `sena-enterprise-ops-alert-webhook/v1` payload to `SENA_ALERT_WEBHOOK_URL` with endpoint-hash evidence and optional HMAC signing from `SENA_ALERT_WEBHOOK_SECRET`. Set `SENA_ALERT_WEBHOOK_TIMEOUT_MS` to tune delivery timeout. Set `SENA_ENTERPRISE_DB_LOCK_TIMEOUT_MS` to tune single-runtime file lock timeout; multi-instance SaaS deployments should use an accepted bridge record with release-gate evidence or replace the local file adapter with a managed database or lock-capable durable storage.

The go-live rehearsal response also includes `sena-enterprise-release-gate-draft/v1`, a release-gate draft that can prefill the workspace review form but keeps human approval and real verifier evidence separate from the generated rehearsal evidence. It also embeds `sena-enterprise-go-live-rollback-drill/v1`; `GET /api/sena/ops/go-live-rehearsal?artifact=rollback-drill` exports the standalone backup, restore-dry-run, incident-alerting, release-gate, and verifier runbook evidence for cutover review. `GET /api/sena/ops/go-live-rehearsal?artifact=post-cutover-monitor` exports `sena-enterprise-go-live-monitor/v1`, a 60-minute observation-window dossier with ops status, firing alert counts, rollback readiness, release verification, exit criteria, next actions, and latest `sena-enterprise-post-cutover-observations/v1` evidence.
Team managers can `POST` the same route to persist `sena-enterprise-go-live-attestation/v1` cutover attestations; approved attestations are rejected until the current rehearsal and persisted post-cutover monitor are ready, while blocked/conditional attestations preserve the rehearsal blockers, release-gate draft status, rollback drill evidence, post-cutover monitor evidence, checklist evidence, and audit trail. The same session plus CSRF protected route accepts `{"action":"start-post-cutover-observation","teamId":"...","environment":"...","releaseVersion":"..."}`, `{"action":"record-post-cutover-sample","teamId":"...","observationId":"..."}`, and `{"action":"complete-post-cutover-observation","teamId":"...","observationId":"...","acknowledgedWarningAlertIds":[]}` to create the fixed 60-minute `sena-enterprise-post-cutover-observation/v1` record required for approved go-live.
The enterprise capability audit is available through `/api/sena/ops/capability-audit` as `sena-enterprise-capability-audit/v1`, mapping the original missing-feature backlog to runnable endpoint, UI contract, artifact, and remaining platform-decision evidence.

Institution email delivery for password resets and team invitations is available through the same notifications endpoint. Set `SENA_EMAIL_WEBHOOK_URL`, optional `SENA_EMAIL_WEBHOOK_SECRET`, `SENA_EMAIL_WEBHOOK_MAX_ATTEMPTS`, and `SENA_EMAIL_WEBHOOK_TIMEOUT_MS`, then call `POST /api/sena/notifications` with `{"action":"deliver-email","teamId":"..."}` to send signed `sena-enterprise-email-webhook/v1` payloads to the approved email bridge. Email delivery payloads include the real recipient address and secure reset/invite action URL only inside the signed email webhook body; the local queue stores them sealed with AES-256-GCM, ordinary in-app notifications keep only email hashes/domains, and team backups exclude `emailDeliveries`.

Audit governance is available through `/api/sena/governance/audit`. Team managers can query JSON, export CSV, or add `?integrity=1` to include `sena-enterprise-audit-integrity/v1`, a scoped SHA-256 linked audit-chain head plus retention evidence. Set `SENA_AUDIT_RETENTION_DAYS` to the institution-approved retention window before production audit retention is claimed. Set `SENA_AUDIT_WEBHOOK_URL`, optional `SENA_AUDIT_WEBHOOK_SECRET`, `SENA_AUDIT_WEBHOOK_MAX_ATTEMPTS`, and `SENA_AUDIT_WEBHOOK_TIMEOUT_MS`, then `POST` the audit endpoint to forward signed `sena-enterprise-audit-webhook/v1` payloads with chain-head evidence to institutional logging or SIEM storage. Forwarded payloads hash email, token, password, invite-code, and secret-like detail fields before delivery.

Upload object-storage delivery is available through `/api/sena/uploads`. Team managers can `POST {"action":"deliver-object-storage","teamId":"...","uploadId":"..."}` to verify the local blob, confirm SHA-256 integrity, and send a signed `sena-enterprise-upload-object-storage-webhook/v1` payload to `SENA_OBJECT_STORAGE_WEBHOOK_URL`; omit `uploadId` to deliver a team batch with an optional `limit`. Payloads include upload metadata, object key, base64 file bytes, declared SHA-256, scan status, and delivery endpoint hash. Files with local scan status `review` are skipped unless `includeReview:true` is provided, and failed local integrity checks audit as `upload.object_storage.fail`. Set `SENA_OBJECT_STORAGE_WEBHOOK_URL`, optional `SENA_OBJECT_STORAGE_WEBHOOK_SECRET`, and optional `SENA_OBJECT_STORAGE_WEBHOOK_TIMEOUT_MS` to connect uploads to institution-approved object storage or a storage bridge.

Managed database sync delivery is available through `/api/sena/governance/backup`. Team managers can `POST {"action":"sync-database","teamId":"..."}` to create a team-scoped sanitized enterprise backup, verify checksum/counts/secret exclusions, and send a signed `sena-enterprise-database-sync-webhook/v1` payload to `SENA_DATABASE_SYNC_WEBHOOK_URL`; `POST {"action":"sync-database","artifact":...}` sends an already exported artifact after the same permission and preflight checks. Payloads use the backup artifact as the canonical sanitized state snapshot, include record counts and payload SHA-256, and never include sessions, SSO state, lockouts, API rate-limit buckets, MFA secrets, email delivery queues, reset tokens, presence, collaboration pub/sub queue events, password hashes, or upload blobs. Set `SENA_DATABASE_SYNC_WEBHOOK_URL`, optional `SENA_DATABASE_SYNC_WEBHOOK_SECRET`, and optional `SENA_DATABASE_SYNC_WEBHOOK_TIMEOUT_MS` to connect the local enterprise runtime to an institution-approved managed database adapter.

Backup restore rehearsal is available through `/api/sena/governance/backup`. `GET` exports a team-scoped backup, `POST` without an action verifies checksum/counts/secret exclusions, `POST {"action":"deliver","teamId":"..."}` creates, verifies, and sends a signed `sena-enterprise-backup-webhook/v1` payload to `SENA_BACKUP_WEBHOOK_URL`, `POST {"action":"deliver","artifact":...}` sends an already exported artifact after permission and core verification checks, `POST {"action":"restore-dry-run","artifact":...}` reports the merge plan without writing restored records, and `POST {"action":"restore","artifact":...}` merges the scoped payload by ID after checksum, record-count, and secret-exclusion checks pass. Set `SENA_BACKUP_WEBHOOK_URL`, optional `SENA_BACKUP_WEBHOOK_SECRET`, and optional `SENA_BACKUP_WEBHOOK_TIMEOUT_MS` to connect scheduled backups to institution-managed storage or a database bridge. Restore never reintroduces sessions, SSO state, lockouts, API rate-limit buckets, MFA secrets, email delivery queues, reset tokens, presence, collaboration pub/sub queue events, password hashes, or upload blobs.

## Interpretation Guardrails

- `A_fusion` is a normalized typed adjacency model, not a causal model.
- Explanatory and ENA-space layouts use position for readability.
- Joint mode is a deterministic `A_fusion` visual embedding and must be reported with weights, normalization, and stability checks; layout distance is not an inferential statistic.
- Human review and coding-reliability documentation are required before using exported interpretations for publication, assessment, or instructional decisions.
