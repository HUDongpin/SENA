## [CRITICAL] Ops session fallback lets any self-registered user reach the deployment-wide ops surface in the SENA_OPS_TOKEN-configured (production) configuration

- **Introduced by the remediation:** yes
- **Evidence:** sena-hk-template/lib/sena/ops-api.ts:110-113 (session fallback when tokens are configured) and sena-hk-template/lib/sena/ops-api.ts:79-86 (`administersAnyTeam` gate); commit a301679 in main..HEAD

**Failure scenario.** Production sets SENA_OPS_TOKEN (the deployment checklist marks it required). At `main`, `requireOpsAccess` threw 401 `ops_token_required` for any caller without a valid bearer token, so the ops surface was bearer-only. After a301679, `resolveOpsAccess` falls through to `opsSessionAccess` whenever no Authorization header is present (ops-api.ts:110-113), and the RBAC gate for a request that names no team is `administersAnyTeam` — any active membership carrying `team:manage` (ops-api.ts:79-86).

Registration is open and unauthenticated: `app/api/auth/register/route.ts:13` POSTs straight into `registerEnterpriseUserAsync`, and with no `inviteCode` the registrant is given a brand-new team with `role = "owner"` and `status: "active"` (lib/sena/enterprise/auth-registration.ts:84-104). `owner` carries `team:manage` (lib/sena/enterprise/access-control.ts:21). There is no invite-only / domain-allowlist / email-verification gate anywhere in the tree. The 201 response sets the `sena_session` cookie immediately.

So: attacker POSTs /api/auth/register with a throwaway email → is instantly an owner of their own team → `administersAnyTeam` is satisfied → they now pass the ops gate for every route that carries no team dimension. Ten such routes exist and none of them take a teamId at all: `/api/sena/ops/status`, `/readiness`, `/metrics`, `/production-evidence`, `/postgres`, `/object-storage`, `/observability`, `/cdn` (all `requireOpsAccess`, zero occurrences of `teamId` in the file), plus `/api/sena/ops/jobs/probe` and `/api/sena/ops/jobs/worker-heartbeat`. That exposes deployment-wide readiness blockers, storage/backup health, hashed webhook endpoints, identity/secret-custody evidence, and the production evidence manifest to any anonymous person who can register.

It is not read-only: `app/api/sena/ops/alerts/route.ts:51-54` uses `requireOpsMutationAccess` and, on `POST {"action":"deliver"}`, calls `deliverEnterpriseOpsAlerts()`, which sends a signed webhook to `SENA_ALERT_WEBHOOK_URL`. CSRF is no obstacle — the attacker mints a CSRF token for their own session. So an unaffiliated registrant can flood the operator's alert channel, and can drive `/jobs/probe` (real dispatch to the configured queue provider) and `/jobs/worker-heartbeat` (writes a synthetic job into the shared store) at will. All of this returned 401 before this branch.

The committed test does not catch it because its negative caller is constructed to be the one shape the gate does stop: `lib/sena/__tests__/ops-api-session-access.test.ts:73-77` builds an invited `coder` and asserts it has no team of its own, with the comment "The member must have no manageable team anywhere, or the gate would pass them for deployment-wide reads for the wrong reason." Meanwhile line 112 of the same file asserts, as correct behaviour, that a plain `registerEnterpriseUser` owner (no invite code — i.e. exactly a self-registered outsider) resolves `{mode:"session"}` for `/api/sena/ops/status` while both ops tokens are configured. I ran it: 5/5 pass. The test pins the vulnerable behaviour as the specification.

**Recommended fix.** Split the gate. Keep per-team `team:manage` only for ops reads that genuinely name a team and re-check it downstream (native-adapters, saas-operations, deployment, jobs?teamId=). For the team-less deployment-wide surface, require an explicit deployment-operator signal rather than "administers any team" — e.g. a `SENA_OPS_SESSION_OPERATOR_EMAILS` allowlist, a designated platform-owner team id, or a dedicated operator role that self-registration cannot mint — and keep mutating ops actions (`/ops/alerts` deliver, `/ops/jobs/probe`, `/ops/jobs/worker-heartbeat`) bearer-only when SENA_OPS_TOKEN is configured. Then add a regression test whose refused caller is a freshly self-registered owner of their own team, not only an invited coder.

## [CRITICAL] Group PatchOp `remove` treats "no resolvable target" as "remove everyone" and silently suspends the whole roster

- **Introduced by the remediation:** yes
- **Evidence:** sena-hk-template/lib/sena/scim.ts:841-849 (`patchScimGroupMembers`, remove branch); alias resolution at scim.ts:777-781

**Failure scenario.** `patchScimGroupMembers` builds `targets` from `[filterValue, ...references.map(e => asString(e.value) || asString(e.email))]`, and `aliasKeys("")` returns `[]` (lookup misses, then `[""].filter(Boolean)`), so a reference that carries neither `value` nor `email` contributes nothing. Line 848 then reads `targets.size === 0` as "match every member" and flips all of them to `active:false`. Any of these bodies hits it: `{"op":"remove","path":"members","value":[]}` (an IdP that batches a delta and computes an empty removal set), `{"op":"remove","path":"members","value":[{"$ref":"https://…/Users/u1","display":"Shared Coder"}]}` (RFC 7643 §4.2 permits a member reference by `$ref`/`display` with no `value`), or `{"value":"  "}` (trimmed to ""). Concretely, using the exact shape of the branch's own passing test at lib/sena/__tests__/scim-route.test.ts:590 — team "Shared Cohort" with an API-provisioned active `owner` plus SCIM-provisioned members — that op reaches `provisionScimGroupResource(..., {scopeMemberStatusToGroup:true})`, every SCIM membership is written `status:"suspended"`, and `activeTeamManagerCount` still sees the API owner, so the `last_team_manager_required` guard never fires: the entire cohort is deprovisioned, persisted, and the route returns 200. The scoping fix that keeps a removal from suspending users globally is what makes this land quietly — nothing else refuses it. (In a SCIM-only team the same op instead 400s on the manager guard, so the bug is invisible to a test suite that only exercises SCIM-owned teams — which is why the existing `remove` tests, which always pass a resolvable `value`, do not catch it.)

**Recommended fix.** Distinguish "the op named no value at all" from "the op named values that resolved to nothing". Track whether `filterValue` was absent AND `operation.value` was absent (`value === undefined`), and only then apply the RFC 7644 §3.5.2.2 remove-the-whole-attribute semantics. If references were supplied but none produced an alias, throw `SenaEnterpriseError(…, 400, "invalid_scim_patch")` — mirroring the guard the add/replace branch already has at scim.ts:857-859 — rather than falling through to the deactivate-all path.

## [MAJOR] Password-reset "production interlock" gates on NODE_ENV alone, not SENA's own production-posture predicate, so it fails open on deployments SENA already treats as production

- **Introduced by the remediation:** yes
- **Evidence:** /Volumes/Starship/SENA/sena-hk-template/lib/sena/enterprise/auth-config.ts:112

**Failure scenario.** `passwordResetTokenExposurePolicy()` computes `productionRuntime = process.env.NODE_ENV === "production"`. Every other production hard-gate in this codebase ORs three more SENA flags onto that test: `enterpriseFileStateWritePolicy` (lib/sena/enterprise/state.ts:601-611) blocks file-state writes on SENA_REQUIRE_PRODUCTION_PERFORMANCE_PATH / SENA_PRODUCTION_EVIDENCE_MANIFEST_REQUIRED / SENA_PLATFORM_SAAS_OPERATING_MODEL_APPROVED, and ops-observability.ts:364-370 and object-storage-adapter.ts:835-841 use the same predicate. Concrete failure: an operator runs a SENA-classified production deployment (SENA_PLATFORM_SAAS_OPERATING_MODEL_APPROVED=1) from a plain `node server.js` / docker-compose process where NODE_ENV is unset or "development", and still carries the pilot flag SENA_PASSWORD_RESET_EXPOSE_TOKEN=1. `productionRuntime` is false, so `enabled` is true, and an anonymous `POST /api/auth/password-reset {"action":"request","email":"victim@org"}` returns `delivery.resetToken` bound to the real user (auth-password-reset.ts:291-296 in the current tree) — full account takeover from knowledge of an email address. The interlock this commit added never fires, while every other SENA gate on that same host does.

**Recommended fix.** Derive `productionRuntime` from the same predicate the rest of the codebase uses (NODE_ENV==="production" || SENA_REQUIRE_PRODUCTION_PERFORMANCE_PATH || SENA_PRODUCTION_EVIDENCE_MANIFEST_REQUIRED || SENA_PLATFORM_SAAS_OPERATING_MODEL_APPROVED), ideally by extracting the existing helper rather than re-deriving it, and add a case to auth-abuse-hardening.test.ts that sets one of those flags with NODE_ENV unset.

## [MAJOR] New per-subject password-reset bucket lets an attacker deny account recovery to any user by email address

- **Introduced by the remediation:** yes
- **Evidence:** /Volumes/Starship/SENA/sena-hk-template/lib/sena/enterprise/auth-password-reset.ts:325

**Failure scenario.** `createEnterprisePasswordResetAsync` now calls `enforceEnterpriseAuthSubjectRateLimitAsync({bucket:"auth.password_reset", subject: normalizeEmail(input.email)})` before anything else; the bucket key contains only the subject (auth-security.ts:295-302), limit 5, window 900s. The route's own limiter is keyed IP|email (api-helpers.ts:129-133) with the same 5/900s budget, so an attacker from a single IP can push exactly 5 requests for victim@org through both. The subject bucket is now full. When the victim then requests a reset from their own IP, their IP bucket is fresh and passes, but the shared subject record increments to 6 > 5 and `applyEnterpriseApiRateLimit` throws 429 api_rate_limited (auth-security.ts:222-237). The victim cannot reset their password for the remainder of the 15-minute window, and the attacker sustains it indefinitely at 5 requests per window. Before this commit the attacker's requests consumed only the attacker's own IP bucket and the victim's request succeeded, so this is a recovery-path DoS the remediation created.

**Recommended fix.** Make the subject backstop non-blocking for the caller: suppress/dedupe the outbound email and still return 202, or count only requests that actually queued a delivery, and give the subject bucket a budget well above the per-IP one so a legitimate holder is never starved by a third party.

## [MAJOR] Unauthenticated password-reset response now discloses the token-exposure policy, including the pilot flag state and the override variable name

- **Introduced by the remediation:** yes
- **Evidence:** /Volumes/Starship/SENA/sena-hk-template/lib/sena/enterprise/auth-password-reset.ts:291

**Failure scenario.** `delivery.tokenExposure = passwordResetTokenExposurePolicy()` is added to `SenaEnterprisePasswordResetRequestResult`, and app/api/auth/password-reset/route.ts:24-30 returns that object verbatim to an anonymous caller with no sanitizer. Any unauthenticated `POST {"action":"request","email":"anything"}` therefore returns `{requested, enabled, productionRuntime, explicitOverride, env:"SENA_ALLOW_PRODUCTION_PASSWORD_RESET_TOKEN_EXPOSURE"}`. On a deployment that still carries the pilot flag the body reads `requested:true, enabled:false, productionRuntime:true` — it tells an anonymous attacker that this deployment is configured to hand out reset tokens and that only the NODE_ENV check is stopping it, and names the exact override variable. Paired with finding 1 this is a ready-made targeting oracle: probe every host/preview/standalone origin until `productionRuntime` reads false, then harvest a real reset token. The pre-fix response leaked at most `mode:"local-token"` when exposure was actually on, and nothing at all when it was off.

**Recommended fix.** Keep the policy object server-side — surface it through the ops/readiness evidence and the auth.password_reset.request audit detail — and drop `tokenExposure` from the public `delivery` payload; the tests at auth-abuse-hardening.test.ts:271-329 can assert on `passwordResetTokenExposurePolicy()` directly instead.

## [MAJOR] Group PatchOp `add` is not idempotent: re-adding an existing member resets their stored role to the fallback

- **Introduced by the remediation:** yes
- **Evidence:** sena-hk-template/lib/sena/scim.ts:853-866 (`patchScimGroupMembers` add/replace branch) and scim.ts:805 (`type: roleFromValue(reference.role ?? reference.type, fallbackRole)`); fallback computed at scim.ts:959

**Failure scenario.** For an `add`, every incoming reference is rebuilt through `members.member(...)`, and `retained` drops any current member whose canonical key collides with an incoming one (both resolve through `canonicalKey` to the same lowercased user id, so an existing member addressed by internal id or externalId always collides). The rebuilt entry takes `type: roleFromValue(reference.role ?? reference.type, fallbackRole)`; a plain SCIM member reference `{"value":"<id>"}` has neither, and the RFC-conformant `{"value":"<id>","type":"User"}` is not an enterprise role either, so both fall back. `fallbackRole` reads `defaultRole` off the group extension, but `directoryGroupToScimProvisioningPayload` (scim.ts:751-754) only emits `{organization, plan}` — the group's declared `defaultRole` is not stored — so the fallback is always `defaultRole(options)` = `viewer`. Concretely: "Genomics Cohort" has a `pi` member and a `coder` member (the branch's own fixture at lib/sena/__tests__/scim-route.test.ts:184-187). The IdP retries a membership push — SCIM clients retry on timeout and re-push on full re-sync — sending `{"op":"add","path":"members","value":[{"value":"<pi user id>"}]}`. The PI is already a member, so the op should be a no-op; instead the membership is rewritten with `role: "viewer"`, silently stripping `team:manage`. If that PI was the team's only active manager the request instead 400s with `last_team_manager_required`, so the IdP's group sync wedges permanently. The suite only covers `add` for a member who is *not* yet in the group (scim-route.test.ts:213-234), so neither outcome is pinned.

**Recommended fix.** In the add/replace branch, when an incoming reference collides with an existing member and the reference carries no explicit role (`reference.role`/`reference.type` does not resolve through `roleFromValue`), merge onto the current entry instead of replacing it — keep the stored `type` and only set `active: true`. Reserve the fallback role for members that are genuinely new to the group. Persisting the group's `defaultRole` on the team record would also stop `defaultRole` from evaporating between POST and PATCH.

## [MAJOR] SCIM DELETE-as-suspend is one-way; the reactivating PATCH reports `active: true` while the stored user stays suspended

- **Introduced by the remediation:** yes
- **Evidence:** sena-hk-template/lib/sena/scim.ts:721-728 (`deactivateEnterpriseScimUser`), scim.ts:591-600 (`replaceScimPath` "active"), scim.ts:200 (`membershipFromRecord` reads only `record.active`), scim.ts:250 (`scimUserResponse` `active: resource.active !== false`)

**Failure scenario.** `deactivateEnterpriseScimUser` calls `replaceScimPath(payload, "active", false)`, which both flags the resource inactive and clears `groups`/`memberships`, so provisioning suspends every membership the user has. There is no inverse: `replaceScimPath` only clears memberships on the `false` branch and never restores them on `true`. Reactivate the user the way every IdP does — `PATCH /Users/{id}` with `{"Operations":[{"op":"replace","path":"active","value":true}]}` — and `patchEnterpriseScimUser` rebuilds the payload from the directory, where each membership now carries `active:false`; `membershipFromRecord` reads *only* `record.active` (ignoring the sibling `status`), so every membership is re-provisioned `suspended`. Nothing changes. But `scimUserResponse` derives its `active` from the request body, so the route answers **200 with `active: true`** while an immediately following `GET /Users/{id}` answers `active: false` (that GET derives `active` from membership status, scim.ts:542). The IdP records the reactivation as successful, stops retrying, and the returning employee has no access. `PUT` does not help either: RFC 7643 §4.1.2 marks User.`groups` readOnly, so no conformant IdP sends the one field that would rebuild the memberships — the only working restore is the SENA-proprietary `path: "memberships"` patch, or a Group PatchOp `add` on each of the user's groups, which then triggers the role reset described in the previous finding. The `replaceScimPath` asymmetry predates this branch, but the DELETE endpoint that makes it the standard deprovision path, and the GET-by-id that exposes the divergence, are both new here, and the new tests only cover the deactivating half (scim-route.test.ts:548-588).

**Recommended fix.** Make the reactivation path real and make the response honest. In `replaceScimPath`, when `active` is set to `true`, restore the memberships that were suspended (or leave them untouched and let provisioning reactivate on an explicit membership list). Change `scimUserResponse`'s `active` to be derived from the provisioning result's membership statuses rather than echoed from the request body, so a request that did not actually reactivate cannot report that it did. Add a round-trip test: DELETE, then PATCH active:true, then GET, and assert GET agrees with the PATCH response.

- **Evidence:** /Volumes/Starship/SENA/sena-hk-template/components/sena/workspace/use-sena-fusion-workspace-main-shell-props.ts:309

## [MAJOR] Import-error drawer effect cannot fire twice for the same error message, so a repeated failure is silent

- **Introduced by the remediation:** yes
- **Evidence:** /Volumes/Starship/SENA/sena-hk-template/components/sena/workspace/workspace-main-shell-section.tsx:127

**Failure scenario.** The new effect depends only on `[importError]`, and no import path clears `importError` before an attempt — `handleContractUpload` sets it only in its catch (use-contract-upload-action.ts:153), `importFilesViaEnterpriseApi` only in its catch (use-enterprise-import-actions.ts:217), `importFilesLocallyWithEnterpriseAdapters` likewise (line 121). Sequence: (1) user uploads a malformed file from the header input (workspace-header-section.tsx:45, which sits in `headerSurfaceRef` — outside the drawer); `importError` becomes 'Unexpected end of JSON input' and the effect opens the drawer. (2) While the drawer is open the header is `inert` (workspace-main-shell-section.tsx:136-147), so the user MUST close the drawer to retry from the header. (3) User closes the drawer, picks the same bad file again. `setImportError` is called with the identical string, so the dep is unchanged, the effect does not re-run, and the drawer stays shut. The user sees nothing at all — exactly the condition the effect's own comment says it exists to prevent ('Without this a failed header upload changes nothing the user can see'). The same happens for any two files that fail with the same message.

**Recommended fix.** Clear `importError` (`setImportError(null)`) at the top of each upload handler before the attempt, or key the effect on an incrementing error sequence/nonce rather than on the message string, so identical consecutive failures still re-open the drawer.

## Lens summaries

### auth-security — 7 candidate finding(s)

Reviewed only the committed range main..HEAD (f99f765..8608071) for the auth/security lens, working from a `git archive HEAD` export in the scratchpad because lib/sena/enterprise/auth-password-reset.ts is being edited concurrently by another agent (all other lens files were byte-identical to HEAD). Ran `npx vitest run` on lib/sena/__tests__/auth-abuse-hardening.test.ts (11 passed) and lib/sena/__tests__/auth-mfa-reset-route.test.ts (3 passed).

Seven findings, three of them material. The strongest is that the new password-reset production interlock (auth-config.ts:112) gates only on `NODE_ENV === \"production\"` while every other production hard-gate in this codebase — file-state write policy, observability sample store, object-storage probe — ORs three SENA_* posture flags onto that test; a deployment those gates already classify as production but which runs without NODE_ENV set will still hand out live reset tokens on an unauthenticated endpoint, so the interlock fails open exactly where it was supposed to hold. Second, the new per-subject password-reset bucket is keyed on the email alone and blocks the caller, so five requests from one attacker IP deny account recovery to the victim for the rest of the 15-minute window, renewably — a regression, since before the change the attacker only consumed their own IP bucket. Third, the policy object added to `delivery.tokenExposure` is returned verbatim to anonymous callers, advertising that a deployment wants to expose reset tokens and naming the override variable; combined with the first finding it is a targeting oracle. Four minor items follow: the interlock also silences the operator-facing `secret-hardening` go-live evidence; the register subject bucket is consumed before validation, so five password-policy rejections lock a legitimate registrant out and an attacker can pre-burn a known address; the MFA per-challenge budget is numerically dominated by the email lockout and its test only passes because it raises SENA_AUTH_LOCKOUT_MAX_FAILURES to 50; and the rate-limit key comment claims no attacker-controlled header enters the key while `x-forwarded-for` remains the first component, with the new test rotating User-Agent instead of XFF.

Checked and found clean, so not reported: subject normalization is safe and consistent (normalizeEmail is trim+lowercase, matching the exact-equality user lookup, and the limiter re-lowercases — no over- or under-matching, no unicode collision path); the MFA-to-lockout coupling cannot lock an account from email knowledge alone because the MFA branch is unreachable without a correct password, and it adds nothing beyond the pre-existing password lockout; challenge deletion is correct on both the exhaustion and success paths, and a sealed-secret failure correctly bypasses the lockout via the error-code guard at auth-login.ts:78; `passwordResetTokenExposure()` is now the single derived accessor, so the interlock genuinely is consulted at every exposure decision point (grep over ops-governance, ops-deployment-readiness, ops-deployment-decisions confirms no second branch reads the raw env); and register's membership role still comes only from `pendingInvite.role` or the hardcoded \"owner\" (auth-registration.ts:76-94) — `selfDeclaredRole` reaches nothing but the audit detail, capped at 80 chars, in a log capped at 5000 entries, with no injection sink or unbounded growth found (the only nit is that the API accepts free text where the UI is a select, which I judged below the reporting bar).

### ops-rbac — 2 candidate finding(s)

The ops job scoping change itself (lib/sena/enterprise/server-job-queue.ts, app/api/sena/ops/jobs/route.ts) held up under attack — I could not break it. The scope is resolved by `scopedServerJobTeamId` before either store is touched (server-job-queue.ts:1380, :1539), so the Postgres and file adapters are covered by the same check rather than one of them being a hole; the Postgres `listJobs` computes its summary under the same WHERE clause (enterprise-postgres.ts:2888-2945), so counts do not leak either. There is no ordering bug: the RBAC check precedes the job lookup, and ownership precedes every lifecycle validation and the write. `requireEnterprisePermission` requires `status === "active"` (access-control.ts:38-46) and session `memberships` are already active-filtered (auth-session.ts:158), so a suspended/invited membership cannot be used. Duplicate `?teamId=` params, non-string body `teamId`, whitespace, and body-vs-query mismatch all fail closed. The bearer path keeps its cross-team reach (`callerScope` is only built for `access.mode === "session"`), and a session caller cannot be mistaken for bearer in either direction.
