001: SENA — Senior-Architect Advisory Report
002: Architectural, algorithmic, and product-engineering review of www.sena.hk against the 2026-07-05 SENA mathematical specification, with a 12-week remediation plan
003: This review is of the artifact, not the author. The junior developer has produced more working software than most prototypes reach, and several instincts in the codebase (block audits, matrix fingerprints, evidence snippets, schema registry) are exactly right. The problem is sequencing and discipline, and both are fixable in twelve weeks.

006: 1. Executive summary
007: SENA's mathematics is publication-grade; its website is a prototype. The July 5 specification defines a single analytic object — the typed block-adjacency matrix A_fusion — and a discipline of declared conventions around it. The site assembles that object correctly in code (lib/sena/model.ts builds S, W, B and the weighted block matrix; lib/sena/fusion-math.ts audits the block equation and fingerprints every matrix). That is real and worth crediting.
008: The core finding, in one sentence: A_fusion exists and optional Joint mode uses it as force-layout weights, but no visible view implements the July 5 declared joint metric embedding with operator, dissimilarity, dimension, seed, exactness, or stress.
009: Workspace geometry has three modes. The default is explanatory, ENA Space uses the vendored jENA library's projected unit/code positions, and Joint mode runs a deterministic force layout over A_fusion weights. None of these is the formal embedding layer required by the July 5 specification: there is still no declared graph operator, eigendecomposition, Schoenberg/MDS check, commute-time distance, metric_exact flag, or stress readout. Person-code proximity therefore remains a visualization aid unless the view is replaced by a proven Phi(A_fusion) embedding with provenance.
010: Classification: the deployment is a research demo wearing a production suit. The marketing site, 60-resource enterprise API (SSO, MFA, SCIM, go-live attestations), and ~30 route-level test suites project a mature SaaS; the analytical core is one monolithic /api/sena/analyze endpoint, a 10,860-line React workspace component, and zero regression tests containing the specification's numbers. It is not yet a maintainable product, and it should not be presented to researchers as one until Section 11's conditions hold.
011: 1.1 Top five blockers to reliable modification in the next 3 months
012: What is genuinely good and must be kept: the A_fusion assembly and its block audit; matrix fingerprints (checksummed S/W/B/G/A_fusion); per-edge evidence snippets tracing edges to interactions and coded segments; the schema registry with versioned response contracts; a synthetic demo dataset (no real student data shipped); reliability tooling (Cohen's kappa / Krippendorff's alpha endpoints); and CONTEXT.md's guardrails, which already forbid silently changing S, W, B, G, A_fusion. The remediation plan builds on these instincts rather than replacing them.
013: The development plan (2026-07-05) is architecturally correct and this report adopts its module map M1–M11 and golden tests T1–T15 wholesale. Two adjustments: its P0–P5 schedule spans 16 weeks; Section 9 compresses to 12 by explicit descoping. And its gap table understates three code-level facts found in this audit: the invented metrics in buildMetrics (a 'concept brokerage' score with a magic 0.5 constant; a neighborContribution = S x B product), the confidence-weighted bridge (B += segment.confidence ?? 1) with undeclared semantics, and the participation matrix Y not being first-class in the data model (G is built from stanza grouping rather than the spec's G_i = X-transpose diag(Y_i) X).

016: 3. Architecture and codebase risks
017: 3.1 Current shape vs the plan's target (M1–M11)
018: The development plan prescribes eleven modules behind one typed data contract, every module returning a provenance record. The current code concentrates M1–M8 inside two files (model.ts builds layers, fusion, metrics, temporal windows; the workspace component owns layout and interaction), has no M5 operator layer, no M6 embedding, no M10 validation, and a partial M11 (report/export exist; no model card or render gate).
019: 3.2 Prototype signatures observed (each with evidence)
020: God component: components/sena/SenaFusionWorkspace.tsx is 10,860 lines — state, math, layout, rendering and copy in one file; workspace/fusion-layout.ts keeps geometry logic in the UI tree.
021: Hard-coded constants: alpha=0.72, beta=0.64, gamma=0.86 (defaultOptions); the 0.5 in conceptBrokerage; canvas clamp margins. None derived, none disclosed.
022: Parallel engines: legacy /api/ena/run (public, 'legacy-ena') beside lib/sena; vendored jena-js and sna-js forks carry their own algorithms — three places epistemic math can drift apart.
023: Contracts inverted: enterprise responses are richly typed and versioned, but the analysis config lacks required declared fields (direction, deg_convention, delta, Phi, d, seed are absent from types and API).
024: Silent fallbacks: B += segment.confidence ?? 1; warnings collected but nothing gates on them; NaN-coercion in audit totals (Number.isFinite ? value : 0).
025: Reproducibility gaps: no seed anywhere in the analysis path; no dataset content-hash; matrix fingerprints exist but are not bound to a dataset version.
026: Test inversion: ~30 test files for auth/ops/SCIM/backup/go-live vs zero math goldens; the pyramid protects the ceremony, not the science.
027: Enterprise theater: SSO, MFA, SCIM, provisioning, go-live rehearsals, attestations, release gates — impressive scaffolding with real maintenance cost, while the analytical core is one endpoint. CONTEXT.md itself calls it a 'readiness loop', i.e., aspiration.
028: PoC persistence: .sena-enterprise/enterprise-db.json file-backed store for auth/team data with an uploads/ directory beside it.
029: 3.3 The one structural decision to make now: where the kernel lives
030: Recommendation: extract a versioned analytics kernel as a TypeScript package (e.g. packages/sena-kernel) containing M2–M8 as pure functions over typed matrices, consumed by both the Next.js app and a server-side compute path for exports/validation. Add an eigensolver via ml-matrix (symmetric EVD is sufficient for L, L_sym, K, and L-pseudoinverse at CSCL scale). Gate the decision with the golden tests: if T10–T11 cannot meet tolerance in JS numerics, or beta datasets exceed roughly 1,500 nodes, stand up a small Python operator service (FastAPI + NumPy/SciPy) implementing M5–M6 and M10 behind the same provenance contract. Do not rewrite M1–M4: they are close to correct and rewriting them burns the schedule. Vendored jena-js/sna-js get pinned versions and nightly parity tests against reference outputs, and are no longer the source of truth for any SENA view.
031: Also decide, and enforce from week 1: a change moratorium on the enterprise/ops surface (freeze, do not delete), and a decomposition budget for the workspace component (extract compute first, presentation later; no file above ~500 lines by week 8).
032: 4. Data model and API issues
033: 4.1 Minimum data contract to enforce
034: The plan's Section 4 contract is adopted with one correction surfaced by this audit: the participation matrix Y must become first-class. Today participation is implicit in stanza grouping, which is exactly why G deviates from the spec's estimator. Enforce with zod schemas registered in schema-registry.ts; validation failures reject ingest with actionable messages.
035: 4.2 Specific risks flagged
036: Ambiguous person IDs: names appear in sample data and uploads; without a pseudonym boundary at ingest, PII propagates into matrices, exports, and share links.
037: Codebook versioning: codebook edits do not version W/B/G today; two analyses under different codebooks are silently comparable in the UI.
038: Window definitions: three window modes exist (stage, moving, turn) but the active rule is not disclosed anywhere user-facing; W and G change meaning with the rule.
039: Raw vs normalized: matrices carry raw and normalized values (good) but exports do not label which is shown, and 'none' normalization makes mixing trivial.
040: Audit trail: per-edge evidence snippets exist (good instinct); formalize as edge -> segment/interaction ID lists in exports so every A_fusion entry is auditable back to source rows.
041: Dataset versioning: no dataset content-hash; runtime bundles cannot prove which data produced them.
042: Export/import schema: runtime-bundle/review-packet exist but their schemas do not include conventions, seeds, or model card; imports do not re-validate.
043: 4.3 Analysis API v2 (service boundaries for the rebuild)
044: Transport can remain Next.js API routes; the boundaries and the provenance envelope are what matter. Heavy operations (embedding, validation) run as background jobs on the existing ops/jobs queue.
045: Deprecations: gate or remove public POST /api/ena/run; freeze /api/sena/analyze as v1-legacy with a sunset note in /docs; the OpenAPI export gains the v2 vocabulary (fusion, normalization, weights, conventions, seeds) that is entirely absent today — grep of the 93KB contract found zero occurrences of any of these terms.
046: 5. Visualization and UX issues
047: Where users are misled today, in order of harm: (1) the Fusion Canvas invites metric reading of person-code proximity that no model supports (F1/F7); (2) role profiles present invented scores as if they were established network measures (F9); (3) attribution surfaces say 'contribution' without person-specific evidence framing (F8); (4) group and temporal comparisons render differences with no uncertainty (F10); (5) the two-ring mental model ('SNA x ENA', 'dual network evidence') is reinforced by marketing, priming users to read the overlay as the method; (6) coordinate clamping quietly distorts even the exploratory geometry at canvas edges (layout.ts).
048: 5.1 Concrete UI changes
049: Fusion view: default Fusion view becomes the joint embedding with an operator picker (Laplacian eigenmaps / MDS + Schoenberg / commute-time) and a persistent provenance strip: operator, delta, d, seed, exact-or-stress. The two-ring overlay remains available, renamed 'Exploratory overlay', permanently badged.
050: Isolated-node panel: side panel listing I0 with reason (fusion-isolated vs social-only-but-bridge-connected, the P3 case); isolated nodes drawn dimmed, never removed.
051: Direction toggle: ingest-level choice with per-view badges; symmetrization is a visible, sticky decision ('Direction collapsed by symmetrization.'), never a default.
052: Attribution inspector: G / G-hat switch; default wording 'associated with windows containing the pair'; 'contributed' appears only when the dataset registers person-specific evidence, and the toggle displays why.
053: Typed centrality: four separate lists (persons on S, codes on W, bridges on B, whole-graph typed with tag); a single mixed ranking is not renderable in the component's props schema.
054: Group/temporal: comparison views require either an attached validation run (test name, n_perm, seed, p) or a 'Descriptive only — no significance test attached.' badge.
055: Exports: every export and share link embeds the model card (items 1–10); rendering and export are blocked while any item is missing — this single gate operationalizes most of the spec's discipline.
056: 5.2 Badge catalog (exact strings)
057: Presentation principle: badges are one line with an info affordance opening the model card; users who ignore them still cannot export uncarded figures. This keeps the conventions visible without burying novices in mathematics.
058: 6. Testing and verification gaps
059: Current state, confirmed: the repo has a healthy vitest habit but the coverage is inverted — approximately 30 suites over auth/ops/enterprise routes and module boundaries, while sena.test.ts (4,986 lines) contains none of the specification's golden numbers, and no test anywhere constructs the worked example. The full strategy, tolerances, CI stages, and suite-by-suite specifications are in the companion document SENA_Test_Strategy_and_CI_Plan_v1.0.md; the test matrix with statuses is a sheet in the companion workbook. Summary:
060: Golden tests first: worked example encoded once as a shared fixture; T1–T15 from the plan are the regression core. Encode in week 1 in expected-fail mode; every red is a ticket; expected-fail reaches zero by end of phase P1 (core) and P2 (embedding).
061: Suites: layer construction (including the no-silent-symmetrization ingest test), admissible-normalization axioms (property-based), fusion assembly identities, directed vs undirected operators, isolated-node conventions on the c4 fixture, Laplacian spectra, Schoenberg check on the non-Euclidean fixture (min eig K = -1.637), commute-time exactness, attribution G/G-hat identities and bounds, API provenance contract, UI provenance/model-card e2e (render blocked when card incomplete), validation reproducibility by seed, security smoke, vendored-lib parity.
062: CI gates: every PR: typecheck, lint, unit/property, T1–T9 + T12–T15, contract tests (< 5 min). Pre-merge: + T10–T11 and Playwright provenance suite. Nightly: 47-check verification suite, sensitivity grids, parity, performance budget. Release: everything green + signed fixture checksums. No deploy while any golden test is red.
063: Verification performed for this report: the spec's worked-example numbers were independently recomputed (NumPy) and all agree — A_fusion fractions, degrees (2, 2.25, 1.25, 2, 8/3, 7/3), spectrum {0, 0.88, 1.88, 2.61, 3.31, 3.81} with one zero eigenvalue, Schoenberg failure at -1.637, rank-2 distortion 0.718 (stress 0.104), commute-time exactness ~1e-13. One methodological caution from that exercise: a naive pairwise checker that builds e_u - e_v without excluding u = v reports a spurious error (~9.28 on this fixture); golden tests themselves need review. Appendix B tabulates the recomputation.
064: 7. Security, privacy, and research-ethics risks
065: SENA analyzes collaborative learning discourse — student words, names, and interaction patterns. The current posture is a prototype's, while the site's surface (registration, uploads, share/export, enterprise claims) is a product's. Confirmed findings:
066: Recommendations proportionate to a proof-of-concept:
067: 1. publish real Privacy, Terms, Security, and Responsible-AI pages before any real-data beta (week 11 gate). Keep them short and honest about PoC status.
068: 2. gate /api/ena/run behind session auth or remove it; verify every analysis/upload route rejects unauthenticated calls (security smoke test S8).
069: 3. pseudonymize at ingest: person_id is opaque; the roster mapping lives in a separate, encrypted store with restricted access; exports and share links never contain the mapping.
070: 4. add consent metadata (instrument, date, scope) and retention/deletion fields to the dataset contract; implement hard deletion honoring them (dataset, matrices, caches, exports).
071: 5. demo/workspace ships synthetic data only (already true — keep it that way) until items 1–4 land.
072: 6. switch beta persistence to the existing Postgres adapter; encrypt uploads at rest; confirm .sena-enterprise is git-ignored and backed up under access control.
073: 7. share links: signed, expiring, card-attached, no PII in URLs; log share/export events to the existing audit route and verify writes.
074: 8. reliability gate: below a declared kappa threshold or human-review coverage, the UI restricts wording to exploratory and the model card says why (item 6).
075: 9. human-review workflow: AI-suggested codes enter analysis only after reviewer adjudication or an explicit 'AI-coded, unreviewed' flag that propagates to every figure.
076: 10. document the data flow one page for ethics boards: what is stored, where, who can see it, how deletion works — reuse the model card vocabulary.
077: 8. Performance and scalability risks
078: CSCL datasets are small by industry standards (tens of persons, tens of codes, hundreds of windows), so correctness-first dense computation is the right default. The costs that bite are cubic operators, resampling, and temporal multiplication — all manageable with caching and background jobs. N = n + m below.
079: Determinism beats speed for this product: pin linear-algebra library versions, run CI eigensolves single-threaded, fix eigenvector sign conventions, and treat cached artifacts as provenance-addressed (dataset_version + config_hash), so identical declarations always reproduce identical figures.
080: 9. Three-month remediation roadmap (12 weeks)
081: This compresses the plan's P0–P5 (16 weeks) into 12 by explicit descoping — the deferred list is part of the commitment. Full task detail, owners, risks and exit criteria are in the companion workbook (Roadmap sheet); phase gates below. Staffing assumed: one senior full-stack architect (0.5–1.0 FTE), one math-literate backend developer (1.0), the existing junior developer (1.0, pairing), UI developer (0.5 from week 6), the PhD reviewer (~0.1 for sign-offs), QA (0.25 from week 8).
082: Dependencies: P1 blocks P2 (operators feed embeddings); P2 blocks the view swap; P3's wording gate depends on the data contract (X_ita) from P0. Biggest schedule risks: JS eigensolver tolerances (fallback decided by golden tests, not debate — see 3.3), beta-dataset consent lead time (start paperwork during P1), and moratorium erosion (the founder must enforce it).
083: What NOT to do during these 12 weeks: no new enterprise features, no new marketing claims, no visual redesign beyond what F1/F7 require, no second dataset format, no multi-language UI. Every one of these has already cost the project more than it returned.

086: 11. Definition of done — ready for the next proof-of-concept stage
087: The SENA website is ready for its next PoC stage when all of the following hold simultaneously (checklist version with verification methods in the companion workbook, sheet 'Definition of Done'):
088: Every displayed quantity — coordinates, distances, centralities, temporal deltas, attribution heatmaps — is computed from A_fusion or A_fusion^dir under declared, recorded conventions.
089: Every graph operator (Laplacians, random-walk, degree-inverse) carries an explicit convention for self-loops, zero-degree vertices (V+ restriction, zero-inverse, or epsilon-regularization with sensitivity), and directedness.
090: Every visible cross-type (person-code) distance carries the operator name, dissimilarity delta, embedding dimension, seed, and either an exact-metric flag (Schoenberg satisfied) or stress/strain.
091: The 15 golden tests pass in CI on every release, with the full 47-check verification suite green nightly; no deploy while any golden test is red.
092: No silent symmetrization: directed inputs remain directed end-to-end; symmetrization is a declared choice with a permanent badge, and B^PC / B^CP are independent in directed mode.
093: No silent deletion of isolated vertices: I0 is computed, retained, reported, and visible.
094: No mixed-type centrality ranking without type labels; the four typed families are the only centrality surfaces.
095: No attribution wording stronger than the evidence: association/exposure by default; contribution only with registered person-specific evidence; G vs G-hat disclosed.
096: A complete model card (data contract, formulas, normalization + divisors, weights + sensitivity, embedding + seed + exactness, coding reliability, evidence traceability, validation, isolated-vertex convention, directed convention) is attached to every rendered figure, export, and share link; rendering is blocked otherwise.
097: All validation results (permutation, bootstrap) are reproducible from recorded seeds; alpha, beta, gamma are never interpreted or compared across normalization rules.
098: Ethics baseline: real Privacy/Terms/Security pages are live; all compute endpoints are authenticated; datasets are pseudonymized with consent metadata before any real-data use.
